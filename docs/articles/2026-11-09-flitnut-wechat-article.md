## 公众号摘要

同一个坑，这个会话踩一遍、你纠正一遍，下个会话原样再踩。我写了个开源 Skill：一句话，把踩坑教训蒸馏成一行行规矩写进 AGENTS.md——120 行硬上限、五道合并闸门、落盘前先经你批准。Claude Code / Codex / Cursor 通用。

## 正文

先说一个你可能很熟悉的场景。

上周 `pnpm build` 挂了，查了半天，是 tsconfig 里的路径别名配错。你把原因讲给 AI，它道歉、改好，态度诚恳。

这周新开会话，你改了另一个别名。`build` 又挂了，挂在同一个地方。

它不是不会，是不知道——你上周教它的东西，留在了上周的会话记录里。AI 的记忆是金鱼式的：换一缸水，昨天的事就沉底了。

结果就是，你的时间大量花在「重新教」上。同样的错它犯三遍，你纠正三遍。

### 一、解法早就有了，但你大概率坚持不下去

很多人知道 AGENTS.md（或 Claude Code 的 CLAUDE.md）：在项目根目录放一个 Markdown 文件，AI 编程工具开工前自动读取。

这个机制有个开源规范，就叫 agents.md（https://agents.md/），Claude Code、Codex、Cursor、Gemini CLI 都认。一份文件，所有工具通用。理论上，你希望 AI 守的规矩，写进去就行。

但「手写手维护」这件事，命运几乎注定：

- 新坑层出，你拼命往里加条目；
- 旧条目过时了，你不敢删——每一条都是踩坑换来的，删哪个都心疼；
- 憋上几个月，文件长成几百行的「常识大全」。真正的规矩淹没在里面，AI 读得敷衍，你自己都不想翻第二遍。

我的规范文件就是这么胖起来的。规范本该是宪法，结果养成了垃圾场。

### 二、让 AI 自己写，行不行？

你可能想过：每次会话结束，让 AI 自己总结经验、自己写进 AGENTS.md，不就完了？

我试过。它交出来的东西有两个问题。

一是**注水**。它会给你写一份几百行的「最佳实践」：一半是「代码要清晰、注释要及时」这种正确的废话；另一半是压根没验证过、就敢写进去的命令——你哪天真照着跑，跑不通。

二是**只增不减**。AI 没有「这份文件要长期被人当真」的立场，它只会追加，不会裁决。文件越长，每一条的分量越轻。

所以缺的不是「写」的能力，是「编辑」的纪律：什么配写进去、什么必须删、写之前要不要核实。

这些恰恰是流程问题。流程问题，就该交给流程工具。

### 三、所以我做了 agentsmd

agentsmd 是一个开源 Agent Skill，要解决的事一句话说得完：**你踩过的坑，AI 不再踩第二遍**。

安装一行：

```bash
npx skills add kelegele/agentsmd-skill
```

装好后，对 AI 说：

> 把这次踩的坑固化成项目规则

然后它会跑完一条完整流水线：收集教训 → 蒸馏成规则 → 读取现状 → 有机合并 → 出方案给你批准 → 落盘 → 顺手同步项目记忆和进度文件。

你全程只干一件事：批准，或者让它改。

规矩全在中间这几步里，这也是它和「让 AI 随手写一份」的区别。

**1️⃣ 三关准入，缺一不写**

每条教训要过三道关：未来大概率再遇到；违反会带来实际损失（返工、bug、浪费时间）；一行能说清。任何一关不过，直接丢弃。「正确的废话」在这一步就被筛掉了。

**2️⃣ 一条规则一行**

所有规则压成一行祈使句，最多带半行原因。比如：「提交前必须通过 lint 和 test；CI 会拦截不合规提交」。没有叙事，没有解释性长段。

**3️⃣ 五道合并闸门，禁止无条件追加**

新规则不是往文件尾部一贴了事，而是和现有条目逐一比对：等价的丢弃、重叠的合并、特例泛化成通用、矛盾的取新、过时的删除。这份文件因此保持「有机整合」，而不是追加日志。

**4️⃣ 120 行硬上限**

整份 AGENTS.md 不超过 120 行（不含空行）。接近上限时必须先删后加；仍有长期参考价值的内容，迁去 `docs/` 里的专题文件，原位置留一行引用——删的是冗余，不是记忆。

**5️⃣ 命令逐条核验**

给新项目生成首版 AGENTS.md 时，写入的每条命令都要实跑确认，或与 package.json scripts / Makefile / CI 配置逐一核对，跑不通的不写。这条是专门治「AI 编命令不打草稿」的老毛病。

**6️⃣ 先批准，后落盘**

所有改动——AGENTS.md、agent 记忆、进度文件、移动文档——先给你看完整方案：新增哪些、合并删除哪些、迁走哪些、总行数多少。你批准之前，它一个字都不动。

### 四、不止写代码的项目

v1.5 加了个实用适配：自动判断 coding / work 两类目录。

代码项目走构建、命令、代码规范那一套；纯文档、数据的协作目录（比如报告库）则换一套语义——扫描对象换成文档结构和命名惯例，规则偏向数据口径、归档和交付流程，归档时参考资料单独归 `references/`。

它还有个收尾动作：看到根目录散落的文档和数据文件（CSV、报表、导出结果堆一层），先全项目查一遍引用，被引用的一律不动，然后出归档方案：文档归 `docs/<主题>/`，数据归 `data/<主题>/`，批准后移动并修复所有链接断点。

做过项目的人都知道，「整理目录」这种事永远排不上优先级。现在它成了收尾时的一句话。

### 五、怎么说，比较容易一次做好

固化本次教训（最常见）：

> 把这次踩的坑固化成项目规则

瘦身一份已经很肥的规范：

> 更新项目规范：把这次的教训按合并决策表整合进去，超 120 行就先删后加

新项目初始化：

> 项目还没有 AGENTS.md，用 agentsmd 生成首版，命令都要实跑核验

顺手归档：

> 把教训写进 AGENTS.md，顺便把根目录散落的文档和数据归整一下

### 六、写在最后

说点背景。

这个 skill 不是什么精巧的发明——AGENTS.md 机制是现成的，蒸馏和合并的思路也是常识。它做的只是把「坚持」这件事流程化：让规矩的维护不再依赖你的自律，而是变成一条谁都能触发、不会走样的流水线。

用下来最大的变化，不是文件变短了（确实变短了），而是我敢用它了。以前几百行的规范，我自己都知道没人会读；现在留在文件里的每一条，都是真金白银换来的，AI 开工前扫一眼就能对齐。连这个 skill 仓库自己的 AGENTS.md，也是按这套规矩养的：发版流程、易踩的坑，都写在里面。

如果你也在用 Claude Code、Codex 或 Cursor，欢迎试试：

- 仓库：https://github.com/kelegele/agentsmd-skill
- 安装：`npx skills add kelegele/agentsmd-skill`

遇到问题或者有想法，去仓库提 issue 就行。

你踩过的坑，就让它值回票价——AI 不再踩第二遍。
